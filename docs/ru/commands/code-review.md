# Code Review

> Режим обзора PR адаптирован из PRPs-agentic-eng от Wirasm. Часть серии рабочих процессов PRP.

**Вход**: $ARGUMENTS

---

## Выбор режима

Если `$ARGUMENTS` содержит номер PR, URL PR или `--pr`:
→ Перейдите к **режиму обзора PR** ниже.

Иначе:
→ Используйте **режим локального обзора**.

---

## Режим локального обзора

Комплексный обзор безопасности и качества незакоммиченных изменений.

### Фаза 1 — GATHER

```bash
git diff --name-only HEAD
```

Если нет изменённых файлов, остановитесь: «Nothing to review.»

### Фаза 2 — REVIEW

Прочитайте каждый изменённый файл полностью. Проверьте на:

**Проблемы безопасности (CRITICAL):**
- Захардкоженные учётные данные, API-ключи, токены
- Уязвимости SQL-инъекции
- Уязвимости XSS
- Отсутствующая валидация ввода
- Небезопасные зависимости
- Риски path traversal

**Качество кода (HIGH):**
- Функции > 50 строк
- Файлы > 800 строк
- Глубина вложенности > 4 уровней
- Отсутствующая обработка ошибок
- Операторы console.log
- Комментарии TODO/FIXME
- Отсутствующий JSDoc для публичных API

**Лучшие практики (MEDIUM):**
- Паттерны мутации (используйте неизменяемость вместо этого)
- Использование emoji в коде/комментариях
- Отсутствующие тесты для нового кода
- Проблемы доступности (a11y)

### Фаза 3 — REPORT

Сгенерируйте отчёт с:
- Серьёзностью: CRITICAL, HIGH, MEDIUM, LOW
- Расположением файла и номерами строк
- Описанием проблемы
- Предложенным исправлением

Блокируйте коммит, если найдены CRITICAL или HIGH проблемы.
Никогда не одобряйте код с уязвимостями безопасности.

## Режим обзора PR

Комплексный обзор GitHub PR — получает дифф, читает полные файлы, запускает валидацию, публикует обзор.

### Фаза 1 — FETCH

Разберите ввод, чтобы определить PR:

| Ввод | Действие |
|---|---|
| Номер (например `42`) | Использовать как номер PR |
| URL (`github.com/.../pull/42`) | Извлечь номер PR |
| Имя ветки | Найти PR через `gh pr list --head <branch>` |

```bash
gh pr view <NUMBER> --json number,title,body,author,baseRefName,headRefName,changedFiles,additions,deletions
gh pr diff <NUMBER>
```

Если PR не найден, остановитесь с ошибкой. Сохраните метаданные PR для последующих фаз.

### Фаза 2 — CONTEXT

Соберите контекст обзора:

1. **Правила проекта** — прочитайте `CLAUDE.md`, `.claude/docs/` и любые руководства для контрибьюторов
2. **Артефакты планирования** — проверьте `.claude/prds/`, `.claude/plans/`, `.claude/reviews/` и legacy `.claude/PRPs/{prds,plans,reports,reviews}/` на контекст, связанный с этим PR
3. **Намерение PR** — разберите описание PR на цели, связанные issue, планы тестирования
4. **Изменённые файлы** — перечислите все изменённые файлы и категоризируйте по типу (источник, тест, конфиг, документация)

### Фаза 3 — REVIEW

Прочитайте каждый изменённый файл **полностью** (не только hunks диффа — вам нужен окружающий контекст).

Для обзора PR получите полное содержимое файлов на head-ревизии PR:
```bash
gh pr diff <NUMBER> --name-only | while IFS= read -r file; do
  gh api "repos/{owner}/{repo}/contents/$file?ref=<head-branch>" --jq '.content' | base64 -d
done
```

Примените чеклист обзора по 7 категориям:

| Категория | Что проверять |
|---|---|
| **Корректность** | Логические ошибки, off-by-one, обработка null, граничные случаи, гонки состояний |
| **Типобезопасность** | Несовпадения типов, небезопасные приведения, использование `any`, отсутствующие generics |
| **Соответствие паттернам** | Соответствие конвенциям проекта (именование, структура файлов, обработка ошибок, импорты) |
| **Безопасность** | Инъекции, пробелы авторизации, раскрытие секретов, SSRF, path traversal, XSS |
| **Производительность** | N+1 запросы, отсутствующие индексы, неограниченные циклы, утечки памяти, большие payload |
| **Полнота** | Отсутствующие тесты, отсутствующая обработка ошибок, неполные миграции, отсутствующая документация |
| **Поддерживаемость** | Мёртвый код, магические числа, глубокая вложенность, неясное именование, отсутствующие типы |

Присвойте серьёзность каждой находке:

| Серьёзность | Значение | Действие |
|---|---|---|
| **CRITICAL** | Уязвимость безопасности или риск потери данных | Обязательно исправить перед merge |
| **HIGH** | Баг или логическая ошибка, вероятно вызывающая проблемы | Следует исправить перед merge |
| **MEDIUM** | Проблема качества кода или отсутствие лучшей практики | Рекомендуется исправить |
| **LOW** | Стилистическая мелочь или незначительное предложение | Опционально |

### Фаза 4 — VALIDATE

Запустите доступные команды валидации:

Определите тип проекта по конфигурационным файлам (`package.json`, `Cargo.toml`, `go.mod`, `pyproject.toml` и т.д.), затем запустите соответствующие команды:

**Node.js / TypeScript** (есть `package.json`):
```bash
npm run typecheck 2>/dev/null || npx tsc --noEmit 2>/dev/null  # Проверка типов
npm run lint                                                    # Линт
npm test                                                        # Тесты
npm run build                                                   # Сборка
```

**Rust** (есть `Cargo.toml`):
```bash
cargo clippy -- -D warnings  # Линт
cargo test                   # Тесты
cargo build                  # Сборка
```

**Go** (есть `go.mod`):
```bash
go vet ./...    # Линт
go test ./...   # Тесты
go build ./...  # Сборка
```

**Python** (есть `pyproject.toml` / `setup.py`):
```bash
pytest  # Тесты
```

Запускайте только команды, применимые к определённому типу проекта. Зафиксируйте pass/fail для каждой.

### Фаза 5 — DECIDE

Сформируйте рекомендацию на основе находок:

| Условие | Решение |
|---|---|
| Ноль находок CRITICAL/HIGH, валидация проходит | **APPROVE** |
| Только находки MEDIUM/LOW, валидация проходит | **APPROVE** с комментариями |
| Любые находки HIGH или сбои валидации | **REQUEST CHANGES** |
| Любые находки CRITICAL | **BLOCK** — обязательно исправить перед merge |

Особые случаи:
- Draft PR → всегда использовать **COMMENT** (не approve/block)
- Только изменения docs/config → более лёгкий обзор, фокус на корректности
- Явный флаг `--approve` или `--request-changes` → переопределяет решение (но всё равно отчитывайтесь о всех находках)

### Фаза 6 — REPORT

Создайте артефакт обзора в `.claude/reviews/pr-<NUMBER>-review.md`, если репозиторий уже не использует legacy `.claude/PRPs/reviews/` для этого рабочего направления:

```markdown
# PR Review: #<NUMBER> — <TITLE>

**Reviewed**: <date>
**Author**: <author>
**Branch**: <head> → <base>
**Decision**: APPROVE | REQUEST CHANGES | BLOCK

## Summary
<резюме в 1-2 предложения>

## Findings

### CRITICAL
<находки или «None»>

### HIGH
<находки или «None»>

### MEDIUM
<находки или «None»>

### LOW
<находки или «None»>

## Validation Results

| Check | Result |
|---|---|
| Type check | Pass / Fail / Skipped |
| Lint | Pass / Fail / Skipped |
| Tests | Pass / Fail / Skipped |
| Build | Pass / Fail / Skipped |

## Files Reviewed
<список файлов с типом изменения: Added/Modified/Deleted>
```

### Фаза 7 — PUBLISH

Опубликуйте обзор в GitHub:

```bash
# Если APPROVE
gh pr review <NUMBER> --approve --body "<резюме обзора>"

# Если REQUEST CHANGES
gh pr review <NUMBER> --request-changes --body "<резюме с требуемыми исправлениями>"

# Если только COMMENT (draft PR или информационно)
gh pr review <NUMBER> --comment --body "<резюме>"
```

Для inline-комментариев на конкретных строках используйте API комментариев обзора GitHub:
```bash
gh api "repos/{owner}/{repo}/pulls/<NUMBER>/comments" \
  -f body="<комментарий>" \
  -f path="<файл>" \
  -F line=<номер-строки> \
  -f side="RIGHT" \
  -f commit_id="$(gh pr view <NUMBER> --json headRefOid --jq .headRefOid)"
```

В качестве альтернативы опубликуйте один обзор с несколькими inline-комментариями сразу:
```bash
gh api "repos/{owner}/{repo}/pulls/<NUMBER>/reviews" \
  -f event="COMMENT" \
  -f body="<общее резюме>" \
  --input comments.json  # [{"path": "file", "line": N, "body": "comment"}, ...]
```

### Фаза 8 — OUTPUT

Отчитайтесь пользователю:

```
PR #<NUMBER>: <TITLE>
Decision: <APPROVE|REQUEST_CHANGES|BLOCK>

Issues: <critical_count> critical, <high_count> high, <medium_count> medium, <low_count> low
Validation: <pass_count>/<total_count> checks passed

Artifacts:
  Review: .claude/reviews/pr-<NUMBER>-review.md
  GitHub: <PR URL>

Next steps:
  - <контекстные предложения на основе решения>
```

## Граничные случаи

- **Нет CLI `gh`**: переключиться на только локальный обзор (прочитать дифф, пропустить публикацию в GitHub). Предупредить пользователя.
- **Разошедшиеся ветки**: предложить `git fetch origin && git rebase origin/<base>` перед обзором.
- **Большие PR (>50 файлов)**: предупредить об объёме обзора. Сфокусироваться сначала на изменениях исходного кода, затем тестах, затем config/docs.
